# 愛の装置｜H3 一括生成セット

RunPodのGPUは**起動中ずっと課金される**ため、27本を人の手で3本ずつ投げると、
生成時間より「次を投げるまでの待ち時間」の方が高くつきます。
このセットは、その待ち時間をゼロにして27本を連続で回すためのものです。

## 入っているもの

| ファイル | 中身 |
|-|-|
| `h3_manifest.json` | 27件の生成指示。プロンプト全文・入力画像名・出力ファイル名が1件ずつ紐付いています |
| `h3_manifest.csv` | 同じ内容の表形式。スプレッドシートで開けます |
| `run_h3_batch.py` | 27本を上から順に生成して、正しい名前で保存するランナー |

## 準備

### 1. キーフレーム画像を9枚、この名前で置く

`batch/keyframes/` フォルダを作って、次の名前で保存してください。

```
AINO_C01_key.png   Cut 1  トランペット奏者
AINO_C02_key.png   Cut 2  音符のリボン
AINO_C03_key.png   Cut 3  愛の装置に手を伸ばす
AINO_C04_key.png   Cut 4  装置の渦
AINO_C05_key.png   Cut 5  舞台全景
AINO_C06_key.png   Cut 6  光の柱
AINO_C07_key.png   Cut 7  花火
AINO_C08_key.png   Cut 8  紙の花火とダンス
AINO_C09_key.png   Cut 9  裸電球の下の演奏
```

**1枚の画像から3本生成します。** 画像は9枚だけで、27枚は必要ありません。

### 2. `run_h3_batch.py` の `generate_one()` を書く

ファイル内で `★ ここだけ書き換えてください` と書かれている関数です。
H3の呼び出し方に合わせて中身を書いてください。RunPod Serverless・
Pod内のローカルAPI・CLIの3通りの書き方をコメントで置いてあります。

**他の場所は触らなくて構いません。**

## 実行

```bash
# まず課金なしで確認（画像が揃っているか、何本走るか）
python run_h3_batch.py --dry-run

# 本番：27本を連続生成
python run_h3_batch.py

# Cut 4 の3本だけ
python run_h3_batch.py --only C04

# 1本だけやり直す
python run_h3_batch.py --only C04P2
```

## なぜ取り違えが起きないか

出力ファイル名は**生成の順番ではなく、マニフェストのidで決まります**。
スクリプトは「どのプロンプトを投げたか」を知った状態で保存するので、

- 完了順が投入順と前後しても
- 途中で何本か失敗しても
- 同時実行しても

出力が入れ替わることはありません。

## 途中で止まったとき

**もう一度同じコマンドを実行するだけです。**
既に出力ファイルがあるジョブは自動でスキップされるので、
生成済みの分に再課金されません。Podが落ちた場合も同じです。

書き込み中のファイルは `.part` という名前で作られ、完成してから
正式な名前に変わります。途中で止まった中途半端なファイルが
「完成済み」と誤判定されることはありません。

## 実行後

出力フォルダに `run_log_日時.csv` が残ります。
どのidが成功・失敗したか、1本あたり何秒かかったかが記録されるので、
次回の見積もりに使えます。

失敗した分は、原因を直して同じコマンドを再実行すれば、その分だけ生成されます。

## コストを下げるために

- **`--dry-run` を必ず先に。** 画像の置き忘れに本番で気づくと、その時間ぶん課金されます
- **Podを起動する前に `generate_one()` を書き終えておく。** 起動してからコードを書くのが一番高くつきます
- **`--workers` は非同期APIのときだけ。** GPUが1枚なら同時実行しても速くならず、タイムアウトのリスクだけが増えます
